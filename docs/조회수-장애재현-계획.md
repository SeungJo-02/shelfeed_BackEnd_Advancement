# 조회수 집계 장애 재현 계획 (Shelfeed / BackEnd_Project)

> PPT(세션-도서SNS-조회수집계.html) 시나리오를 실제 프로젝트에서 재현: 문제 발생 → 탐지 → 해결 → 재발 방지
> 현황: 모니터링 스택(Prometheus/Grafana/k6/InfluxDB) 있음, mysql-perf(3308, CPU 0.6) 있음.
> 없음: viewCount 컬럼, mysqld_exporter, Kafka, ClickHouse, 로컬 Hikari 풀 설정(기본 10)

## Phase 2 — 탐지 (용의자 표 실측, 각 단계 Grafana 캡처 = 블로그 재료)
1. p99 상승 확인 (`http_server_requests_seconds`) — 상세+배경 API 동반 상승
2. RPS — 몇 배 안 됨 → 무죄
3. #7362: Threads Running·CPU·Slow Queries 전부 평온, 슬로우 0 → 무죄
4. #20729: **Pending·Max acquire 급증** → 증상 발견
5. `SELECT * FROM sys.innodb_lock_waits\G` + `SHOW GLOBAL STATUS LIKE 'Innodb_row_lock%'` → 같은 id UPDATE끼리 대기 = **진범**

## Phase 3 — 응급 조치 실험

## Phase 4 — 근본 해결 (Kafka + ClickHouse)
- [ ] docker-compose에 Kafka(KRaft 단일노드) + ClickHouse 추가 (리소스 상한 주의)
- [ ] `POST /api/v1/reviews/{id}/view`: Redis SETNX+TTL 30분 → Kafka `review.view.v1` 발행 → 204 (MySQL 무접촉)
- [ ] ClickHouse: Kafka Engine 테이블 → MV → AggregatingMergeTree (`uniqState(event_id)` 중복 방어)
- [ ] 스케줄러 1분 주기 CH 집계 → Redis → 상세 API는 Redis만 읽음
- [ ] 전환은 PPT STEP 1→3: 배치 UPDATE → 이중 기록·대조 → 읽기 전환 (단계별 PR)
- 클라이언트 3초 체류(IntersectionObserver)는 블로그 설명용, 재현은 k6 직접 호출

## Phase 5 — 재측정 + 재발 방지

## ✅ 재현 실행 절차 확정 (2026-09-15 실측으로 검증)

```bash
docker compose up -d                                   # mysql-perf(3308)·exporter·prometheus·grafana·influx·ES
DB_URL='jdbc:mysql://localhost:3308/shelfeed?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul' \
JAVA_TOOL_OPTIONS="-Xmx1g -Xms512m" \
./gradlew bootRun --args='--spring.profiles.active=local,mock-aladin --spring.jpa.show-sql=false'
bash k6/setup-ids.sh                                   # PUBLIC 리뷰·실제 회원 ID 풀 → k6/ids.local.json
k6 run k6/setup-tokens.js                              # 토큰 50개 (수명 1시간 — 실행 직전에)
k6 run --out influxdb=http://localhost:8086/k6 --summary-trend-stats="avg,p(95),p(99),max" \
       --summary-export k6/results/view-storm-before.json k6/view-storm.js   # 총 10분
```

### 첫 실행에서 밟은 함정 (전부 스크립트/절차에 반영)
- 8080에 다른 프로젝트(timekorea-api)가 IPv4로 붙어 있어 k6·Prometheus가 엉뚱한 서버를 봤다 → 내리고 재시작
- `.env`의 DB_URL은 3307(mysql)이라 exporter가 보는 mysql-perf(3308)에 트래픽이 안 갔다 → DB_URL 덮어쓰기
- 기본 HOT_ID=1이 PRIVATE 글이라 폭풍 요청 전부 403, 락 보유 시간이 짧아 재현 실패 → 기본 3(PUBLIC)
- 배경 유저 ID 1~40은 존재하지 않아(회원은 347~897) 전부 404, 리뷰 2~700에 PRIVATE 155개 섞여 403 → setup-ids.sh
- `mock-aladin` 없이 띄우면 검색이 실제 알라딘 API를 트랜잭션 안에서 호출해 평시 p99·usage max를 오염 → 프로필 추가
- 토큰 수명 1시간. 예전 토큰으로 돌리면 401
- `local` 프로필 `show-sql: true`는 200 VU에서 병목 → 실행 인자로 끔

### 1차 정상 실행(21:12~21:22, HOT_ID=3, BG 30 / STORM 200 VU) 실측 요약
- 폭풍 max: 유입 301 req/s · Pending 160 · Active 8/8 · acquire max 1.71s · usage max 2.60s · 행 락 대기 279/s · 평균 28ms · current waits 8 · Threads running 10 · QPS 6,243 · 슬로우 0 · 호스트 CPU 12%
- k6 p95: 인기글 상세 663ms · 다른 글 상세 558ms · 피드 578ms · 검색 609ms · 로그인 384ms — 조회수와 무관한 API가 같이 느려지는 것은 재현됨
- 발화 알람: ① Pending, ② Acquire, ③ RowLockWaits. ④ 평균 100ms는 미발화(풀 8이라 DB 안 대기가 짧다)
- 5xx 0건 (로컬 connection-timeout 기본 30s, acquire max 1.7s) → 블로그의 성공률 하락 서사는 실측으로 다시 써야 함
- 시나리오와 다른 점: Threads running 3이 아니라 10, QPS는 평탄이 아니라 14배 증가, 대기의 대부분은 DB 행 락(28ms)이 아니라 커넥션 풀 앞(Pending 160)
- 이 실행은 배경 403/404·알라딘 호출로 평시 값이 오염돼 있어 폐기. **2차(21:26~21:36, 전 요청 200) 실측은 `docs/blog/실측-2026-09-15-view-storm.md`**

- **실측 2 (23:01~23:12, STORM 1,200 VU · RAMP 1m · BG 60 · Tomcat 2000 · timeout 5s)**: 상세 p99 7.1s, 그 외 8.3s, Pending 1,193, 5xx 285건 — 블로그 본문용. `docs/blog/실측-2026-09-15-view-storm.md` 실측 2 절
- **실측 3 (09-16 03:25~03:36, STORM 1,200 · BG 100 · RAMP 1m)**: 유입 94→252(2.7배), 상세 p99 67ms→11.2s, 그 외 12.2s, Pending 1,295, 성공률 79%, 5xx 14,708 — **블로그 도입부용**. BG 170으로 2.0배를 맞추면 평시부터 풀 포화(폐기)

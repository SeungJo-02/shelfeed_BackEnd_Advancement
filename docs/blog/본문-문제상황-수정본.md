## 슬로우 쿼리 로그에는 다섯 줄이 남았다

**[그림 5]** 터미널 캡처

> MySQL 8.0 · mysql-perf 슬로우 쿼리 로그 (`long_query_time=1`) · 폭풍 구간. 남은 다섯 건이 전부 같은 UPDATE이고, 실행 시간 1.0초 중 1.0초가 락 대기다 · 빨간 표시는 판단 기준을 짚은 것

```
# Time: 2026-09-16T03:29:54 (KST)
# Query_time: 1.000728  Lock_time: 1.000122  Rows_sent: 0  Rows_examined: 1
update reviews r1_0 set view_count=(r1_0.view_count+1) where r1_0.review_id=3;
```

검사한 행은 1개, 실행 시간은 1.0초, 그중 락 대기가 1.0초다. 쿼리가 느린 게 아니라 기다린 것이다.

문제는 이게 다섯 줄뿐이라는 점이다. 폭풍 구간 내내 초당 234건씩 락 대기가 일어났는데 그중 1초를 넘긴 건 다섯 건이었다. 나머지 수십만 건은 평균 33ms를 기다리다 통과했으니 `long_query_time=1`에 걸릴 일이 없다.

**슬로우 쿼리 로그는 개별 쿼리를 보지, 경합을 보지 않는다. 이 로그만 보고 있었다면 "가끔 느린 UPDATE 다섯 건"으로 읽혔을 것이다.**

## 커넥션 풀이 비어 있었다

**[그림 6]** `커넥션 풀 (HikariCP)` 행 두 패널

> Grafana · HikariCP · 03:25 → 03:37. Pending 최대 1.30K, Active 8(= Max 8), Idle 0. Max acquire 5.18s(타임아웃 5초에 닿음), Max usage 5.07s, Max creation 3ms · 빨간 표시는 판단 기준을 짚은 것

| 지표 | 평시 | 폭풍 | 변화 |
|---|---|---|---|
| Active | 0.8 | 8 (= Max) | 풀 소진 |
| Idle | 7 | 0 | 풀 소진 |
| Pending | 0 | 1,295 | +1,295 |
| Max acquire | 수십 ms | 5.18 s | 타임아웃에 고정 |
| Max creation | 3 ms | 3 ms | 변화 없음 |

커넥션 8개가 전부 나가 있고 1,295개가 줄을 섰다. 여기서 두 가지를 읽을 수 있다.

첫째, creation이 평평하다. 커넥션을 새로 만드느라 느려진 게 아니다.

둘째, acquire가 5.18초에서 멈췄다. 커넥션 타임아웃이 5초라 그보다 오래 기다린 요청은 지연으로 잡히지 않고 앞 절의 5xx로 빠졌다.

**풀이 작아서가 아니다. 나간 커넥션이 돌아오지 않아서 비었다. 그렇다면 무엇을 기다리고 있었나.**

## 커넥션을 붙잡고 있던 건 한 행의 락이었다

**[그림 7]** `MySQL — InnoDB 락` 행 두 패널

> Grafana · InnoDB 행 락 · 03:25 → 03:37. 행 락 대기 발생률 최대 234/s(평균 88.7), 현재 대기 중 최대 8, 평균 락 대기 시간 최대 93.6ms(평균 33.3ms). 회색 점선은 알람 임계 · 빨간 표시는 판단 기준을 짚은 것

**[그림 8]** 터미널 캡처

> MySQL 8.0 · `sys.innodb_lock_waits` · 폭풍 구간. 막는 쪽과 막히는 쪽이 같은 쿼리, 같은 review_id다 · 빨간 표시는 판단 기준을 짚은 것

```
locked_table   : `shelfeed`.`reviews`
locked_index   : PRIMARY
locked_type    : RECORD
waiting_query  : update reviews r1_0 set view_count=(r1_0.view_count+1) where r1_0.review_id=3
blocking_query : update reviews r1_0 set view_count=(r1_0.view_count+1) where r1_0.review_id=3
```

서로 다른 두 요청이 충돌한 게 아니다. 같은 요청 수십 개가 한 행 앞에 한 줄로 서 있었다.

여기서 락 평균 대기 시간이 33ms밖에 안 된다는 점이 의아할 수 있다. 락 앞에 설 수 있는 세션은 커넥션 풀 크기인 8개가 상한이기 때문이다. 나머지는 DB에 들어가지도 못하고 앞 절의 Pending 1,295로 쌓인다. 그래서 한 건당 대기는 짧아도 총량은 전혀 짧지 않다.

| 근거 | 값 | 뜻 |
|---|---|---|
| 락 대기 발생 ÷ 인기글 요청 | 152/s ÷ 189/s | 인기 감상글 요청 5건 중 4건이 락 앞에 섰다 |
| 락 대기에 쓰인 커넥션 시간 | 초당 5.94 커넥션-초 ÷ 풀 8 | 풀 전체 시간의 74%가 락 대기였다 |
| 동시 락 대기 세션 | 평균 4.5, 최대 8 | 최대치가 풀 크기와 같다 |

**한 건이 오래 기다린 게 아니라 모든 커넥션이 거기 묶여 있었다. 원인은 한 행인데 피해는 서비스 전체였다.**

풀을 8에서 20으로 늘리면 뭐가 좋아지는지 계산해봤다
계산 노트
// 같은 행을 기다리는 구간에서 처리량 상한은 커넥션 수가 아니라 락 보유 시간이 정한다
한 행의 처리량 상한  =  1 / 락 보유 시간(T)

// 사건 구조: UPDATE가 트랜잭션 맨 앞 → T = 뒤따르는 조회 5번 + 응답 조립
T ≈ 12ms            →  1 / 0.012s  ≈  80 건/s
인기글 유입          =  198 건/s   →  매초 118건이 줄에 남는다
줄이 길어질수록 대기가 T에 더해진다   →  평균 대기 3.9s

// 풀 8 → 20
T 그대로             →  처리량 80 건/s 그대로
달라지는 것          →  줄 서는 자리 (앱 풀 앞 대기 → DB 안 행 락 대기)
늘어나는 것          →  DB 세션 12개, 유지 비용

// UPDATE를 트랜잭션 맨 뒤로
T ≈ UPDATE 자체 0.1ms (+커밋)   →  약 10,000 건/s
남는 것              →  읽기 요청이 쓰기를 만드는 구조 그대로
선택지한 행 처리량풀 고갈까지읽기 경로의 쓰기비용
풀 8 → 2080 건/s (그대로)조금 늦어짐남음DB 세션 12개 추가
UPDATE를 트랜잭션 뒤로약 10,000 건/s사실상 없음남음코드 한 줄
읽기 경로에서 쓰기 제거상한 없음없음0설계 변경
풀을 늘려 사는 건 처리량이 아니라 풀이 빌 때까지의 시간이다. UPDATE를 뒤로 옮기면 락 보유 시간은 줄지만, 트래픽에 비례해 쓰기가 생기는 구조는 그대로다. 12ms·0.1ms는 시나리오 값이라 재현 후 실측으로 바꾼다.

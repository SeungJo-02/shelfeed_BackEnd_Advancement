## 3. 절별 내용 수정 포인트

### 배경
- 그대로 두되 종결어만 정리(`~서비스이다. ~서비스이다.` → 한 문장).
- 마지막에 트랜잭션 구성을 한 줄 추가하면 9절 복선이 된다: "요청 하나가 쓰기 1번과 읽기 5번을 한 트랜잭션에 묶는다."

### 2절 (요청 쇄도)
- `[상황] [결론]` 라벨 제거, 문장으로 잇는다.
- 빈칸 채우기: `{X}ms->{y}s` → 67ms → 11.2s, 다른 기능 → 111ms → 12.2s, `{}배` → 2.8배 / 167배.
- "부하가 선형이 아닌 비선형적으로" → **"부하는 선형으로 느는데 지연이 비선형으로 터졌다"** (주어가 뒤집혀 있다)
- "로그인·검색·로그인" 중복, "도서감상피드" → "인기 감상글"로 통일.

### 3절 (관측된 지표 → 알림/오진)
- `성공률 {}%->{}%` → 100% → 43%, `P99 {}ms->{}s` → 67ms → 11.2s, `커넥션 8/8` → Active 8 / Max 8, Pending 1,295.
- "감상글 상세 P99만 Firing" 뒤에 한 줄 추가: **"나머지가 정상이어서 조용했던 게 아니라, 커넥션 풀·행 락 룰은 그때 아예 없었다."** 이 한 줄이 재발 방지 절의 근거가 된다.
- "DB CPU·메모리 등에도 문제가 없는 것을 확인했다" → 이 스택은 컨테이너 CPU·메모리를 못 잰다. **"QPS·슬로우 쿼리·Threads running에도 문제가 없었다"** 로 교체.
- N+1 의심은 좋은 오진이다. 처음 생각 → 왜 틀렸나 → 남은 것 3단으로 정리하면 참고 블로그의 형식과 같아진다.

### 4절 (공유자원 후보 — DB / 커넥션 풀)
- `Peak Threads Running, Max Used Connections, Buffer Pool, QPS 모두 평시 수준` → 실측은 Threads running이 2 → 10으로 **올랐다**. QPS도 6배 늘었다. 문장을 "DB가 더 많은 일을 하느라 느려진 게 아니다(QPS는 오히려 늘었고 슬로우 쿼리와 CPU는 여유)"로 바꾼다.
- `Pending 24` → **1,295**. `Max acquire, Max usage 각각 {}s,{}s` → **acquire 5.18s, usage 5.07s, creation 3ms**.
- "어플쪽 문제는 아니라고 생각했고" → 원인은 앱 코드다. **"앱이 일하느라 느린 게 아니라 기다리는 중이었다"** 로.
- creation이 평평하다는 점을 한 줄 넣으면 "커넥션을 새로 만드느라 느린 것도 아니다"가 닫힌다.

### 5절 (범인)
- "UPDATE 쿼리가 DB Row Lock으로 잠겨 있는 동안" → 방향 반대. **"UPDATE가 그 행에 X락을 걸고 커밋까지 놓지 않는 동안"**.
- "서비스 전체가 다운" → 성공률 43%, p99 11초다. **"서비스 전체가 느려지고 절반 가까이 실패했다"**.
- 락 평균 대기가 33~94ms로 짧은 이유를 한 문단 넣어야 독자가 막히지 않는다(락 앞 대기열이 풀 8로 묶여 있음). 그 자리에 총량 근거 표를 넣는다: 인기글 요청의 80%가 락 대기, 풀 시간의 74%가 락 대기, 동시 대기 세션 최대 8 = 풀 크기.

### 6절 (어떻게 해결할까)
- 풀 확대 기각을 정량으로. `한 행의 처리량 = 1 / 락 보유 시간`, 풀을 늘려도 처리량은 그대로이고 줄 서는 자리만 앱에서 DB로 옮겨간다.
- UPDATE를 뒤로 미루는 안의 기각 근거를 "트래픽이 더 몰리면 같은 상황"이 아니라 **"읽기 요청이 쓰기를 만드는 구조가 그대로"** 로.

### 7절 (해결방안)
- "봇은 JS를 실행하지 않으니까" → Googlebot과 헤드리스 크롤러는 실행한다. **"단순 크롤러와 링크 미리보기 봇은 걸러진다"** 로 좁힌다.
- SETNX 설명 교체: SETNX에는 만료가 없고 deprecated다. **`SET key 1 NX EX 1800`** 한 번에 해야 원자적이다. "중복되면 취소"가 아니라 "이미 있으면 아무것도 하지 않고 false를 돌려준다".
- Kafka: "at-least-once를 지향한다" → 컨슈머 오프셋 커밋 방식의 기본 결과. UUID만으로 멱등성이 보장되지 않고 **받는 쪽이 그 id로 걸러야** 한다.
- ClickHouse: append-only가 아니다(UPDATE/DELETE는 mutation). "집계 및 집계" 중복. 단건 조회에 약한 주된 이유는 압축보다 **희소 인덱스의 8,192행 그래뉼과 컬럼별 파일**.
- "ClickHouse가 뻗어버리는" → "병목이 되기에".

### 8절 (재발 방지)
- "알람에 4가지" 뒤에 6개가 나열된다. **"발화 룰 4개 + 일부러 안 울릴 대조군 2개"** 로.
- 빈칸 채우기: 2번 `{n}배` → 평시 45ms의 **20배**. 3번 → 평시 0.5/s의 **약 300배, 사건 234/s의 1/6**. 4번 → **상세 p99 예산 300ms의 1/3**.
- 5·6번에 `for: 5m` 누락.
- "1~4번까지 Firing이고 5~6번이 DB문제가 아니라…" 문장 꼬임 → **"1~4번이 Firing인데 5~6번이 Normal이면, DB가 느린 게 아니라 앱이 DB를 기다리는 중이라는 걸 알림 목록만 보고 읽을 수 있다."**
- 실측에서 ④(평균 100ms)는 울리지 않았다(최대 94ms). 그 사실을 적고 "풀이 작을수록 DB 안 대기는 짧아 ④는 늦게 울린다"를 덧붙이거나 임계를 50ms로 낮춘다.
- "지표가 없어서가 아니라 대시보드에 없었어서" → 실제 공백은 **알람 룰**이었다(등록된 룰이 상세 p99 하나뿐).

### 9절 (회고)
- `~부분.` 여섯 번 반복 → 각 항목을 문장으로 끝낸다.
- "모놀리식에서 CQRS를 경험" → 범위를 좁혀 **"조회수에 한해 쓰기 경로와 읽기 모델을 분리해 봤다"**.
- 마지막 두 문장을 하나로 합친다.

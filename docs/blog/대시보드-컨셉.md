# 블로그 파트별 대시보드 컨셉

> 만들기 전 설계. 파트(블로그 절) → 그 절이 그림으로 증명할 문장 → 들어갈 요소.
> 참고: Claude Design 캔버스 `Shelfeed 조회수 행 락 보드`(아트보드 20개), 삭제된 `shelfeed-view-lock.json`(5행 14패널).

---

## 설계 원칙 4개

1. **블로그 절 = 대시보드 행 = 스크린샷 한 장.** 행 하나만 펼쳐 캡처하면 그 절의 그림이 된다. 절을 넘나드는 패널은 두지 않는다.
2. **한 패널은 한 문장만 증명한다.** 증거가 둘이면 패널을 쪼갠다. 캡션도 한 줄로 끝나야 하기 때문이다.
3. **모든 패널의 시간 범위에 평시 구간을 포함한다.** 배수를 캡션에서 읽게 하지 않고 그림에서 눈으로 읽게 한다 (평시 2분이 왼쪽에 평탄하게 남아야 한다).
4. **알람 임계는 전부 패널에 점선으로 그린다.** 알림 화면의 숫자와 그림의 숫자가 같아야 재발 방지 절이 성립한다.

## 데이터소스 역할 분담 — 이번 설계의 핵심 결정

| | Prometheus | InfluxDB-k6 |
|---|---|---|
| 무엇을 보나 | **서버가 본 것** — 공유 자원(풀·락·DB) | **클라이언트가 본 것** — API별 체감 지연 |
| 인기글 한 건과 다른 글 구분 | **불가.** Micrometer가 uri를 `/api/v1/reviews/{reviewId}`로 템플릿해서 두 요청이 같은 시계열에 합쳐진다 | **가능.** k6가 `api` 태그로 분리 (`hot_detail` / `bg_detail` / `bg_feed` / `bg_search` / `bg_login` / `bg_comments` / `bg_user` / `bg_genre` — InfluxDB에서 실측 확인) |
| 담당 파트 | 4·5·7·8·14 (원인 쪽) | 2·3 (증상 쪽) |

**왜 중요한가** — 블로그 2절의 핵심 문장이 "인기 감상글 RPS만 239로 오르고 피드 33.8·검색 28.6은 그대로다"다. 이 문장은 Prometheus만으로는 그릴 수 없다. 인기글과 다른 글이 같은 uri 라벨에 합쳐지기 때문이다. **인기글을 따로 세우는 라인은 반드시 k6(InfluxDB) 쪽에서 뽑아야 한다.**

# 파트별 요소

## 파트 0 — 도입부 (히어로)

**그림이 증명할 문장**: 유입은 2.8배인데 응답은 167배, 그리고 DB는 한가했다.
**행 이름**: `① 개요 — 한 화면 요약` · 캔버스 대응: `Main`, `ObservedStats`

| # | 요소 | 타입 | 쿼리 | 그림에서 읽을 수치 |
|---|---|---|---|---|
| 0-1 | 유입 (전체 RPS) | stat + 스파크라인 | `sum(rate(http_server_requests_seconds_count{uri=~"/api/v1/.*"}[1m]))` | Max |
| 0-2 | 감상글 상세 p99 | stat + 스파크라인 | `histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket{uri="/api/v1/reviews/{reviewId}"}[1m])))` | Max |
| 0-3 | 성공률 (2xx+3xx) | stat + 스파크라인 | `sum(rate(...{status=~"2..|3.."}[1m])) / sum(rate(...[1m]))` | **Min** (최저 성공률) |
| 0-4 | HikariCP Pending | stat + 스파크라인 | `hikaricp_connections_pending{application="shelfeed"}` | Max |
| 0-5 | InnoDB 행 락 평균 대기 | stat + 스파크라인 | `rate(mysql_global_status_innodb_row_lock_time[1m]) / rate(mysql_global_status_innodb_row_lock_waits[1m])` | Max |

- 타일 5개 고정. 캡션 한 줄에 다섯 숫자가 그대로 들어가야 하므로 늘리지 않는다.
- 각 타일 계산은 **Max 하나만** 쓴다. 평시값은 패널이 아니라 캡션이 책임진다 (Grafana stat은 "평시 → 폭풍" 두 칸을 한 타일에 못 그린다. 캔버스의 두 줄 타일은 재현 그림이었다).
- 0-3만 Min인 이유: 성공률은 떨어지는 지표라 Max를 쓰면 100%가 찍힌다. 삭제된 대시보드 원본(패널 id107)을 확인한 결과 **이미 `calcs: ["min"]`이었다.** 바꿀 것이 아니라 새로 만들 때 잃지 말아야 할 설정이다.

## 파트 1 — 배경

**대시보드 요소 없음.** 코드 구조 설명만. (트랜잭션이 쓰기 1번 + 읽기 5번을 묶는다는 한 줄이 9절 복선)

## 파트 2 — 유입은 2.8배인데 응답은 167배 느려졌다

**그림이 증명할 문장**: 유입이 는 건 감상글 상세 하나뿐인데, p99는 넷이 같은 시각 같은 모양으로 꺾였다.
**행 이름**: `② HTTP — 증상` · 캔버스 대응: `ApiP99`, `Rps`

| # | 요소 | 타입 | 데이터소스 / 쿼리 | 그림에서 읽을 수치 |
|---|---|---|---|---|
| 2-1 | API p99 — 감상글 상세 vs 그 외 전체 | timeseries (2선) | Prom · `histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket{uri="/api/v1/reviews/{reviewId}"}[1m])))` / 같은 식에 `uri=~"/api/v1/.*", uri!="/api/v1/reviews/{reviewId}"` | 두 라인의 Max, 꺾이는 시각이 같은지 |
| 2-2 | **[신규]** API별 p99 — uri 개별 | timeseries (uri별) | Prom · `histogram_quantile(0.99, sum by (le, uri) (rate(http_server_requests_seconds_bucket{uri=~"/api/v1/.*"}[1m])))` | 피드·검색·로그인·댓글 **각각의** Max |
| 2-3 | API별 RPS | timeseries (uri별) | Prom · `sum by (uri) (rate(http_server_requests_seconds_count{uri=~"/api/v1/.*"}[1m]))` | 한 줄만 솟고 나머지는 평탄 |
| 2-4 | **[신규]** k6 체감 지연 — api 태그별 p99 | timeseries | **InfluxDB-k6** · `SELECT percentile("value", 99) FROM "http_req_duration" WHERE $timeFilter GROUP BY time($__interval), "api" fill(none)` | `hot_detail` 라인과 무관한 API 라인이 겹쳐 오르는 모양 |
| 2-5 | **[신규]** k6 API별 RPS | timeseries | **InfluxDB-k6** · `SELECT count("value") FROM "http_reqs" WHERE $timeFilter GROUP BY time(10s), "api" fill(0)` + Math 변환 `$A / 10` | `hot_detail`만 오르고 `bg_*`는 평탄 |

- **2-2가 리뷰에서 나온 보강이다.** 본문 2절 표는 피드 57ms→11s, 검색 98ms→14s, 로그인 131ms→8.4s를 **개별로** 인용하는데, 2-1은 "그 외 전체"로 합쳐 버려 이 세 숫자를 그림에서 못 읽는다. 피드·검색·로그인은 애초에 uri가 달라 Prometheus로 분리된다.
- 2-1은 남긴다. 알람 ⓪과 PromQL이 같아 **"알람이 본 그림"**이기 때문이다(파트 4와 이어진다).
- 2-3의 감상글 상세 라인은 캡션에서 이름을 정직하게 쓴다. 그 라인은 "인기글"이 아니라 **"감상글 상세 전체"**다.
- 2-4·2-5는 **한 쿼리로 8개 시리즈**가 나온다(k6 Trend 6개를 따로 부를 필요 없음). `http_req_duration`·`http_reqs`에 `api` 태그가 실재함을 InfluxDB에서 확인했고, 위 GROUP BY 쿼리로 `hot_detail`/`bg_detail`/`bg_feed`/`bg_search`/`bg_login`/`bg_comments`/`bg_user` p99가 실제로 분리돼 나오는 것까지 확인했다.
- 서버측(Prometheus) p99와 클라이언트측(k6) p99는 **다른 측정치다.** 네트워크·클라이언트 대기가 k6 쪽에만 포함되므로 두 숫자는 일치하지 않는다. 본문 표에 쓸 숫자는 **하나만 고르고**, 어느 쪽인지 캡션에 밝힌다.


## 파트 3 — 사용자에게는 지연이 아니라 실패로 보였다

**그림이 증명할 문장**: 커넥션을 5초 안에 못 받은 요청이 500이 됐고, 두 건 중 한 건이 실패하는 구간이 생겼다.
**행 이름**: `③ HTTP — 사용자 영향` · 캔버스 대응: `ErrorRate`

| # | 요소 | 타입 | 쿼리 | 그림에서 읽을 수치 |
|---|---|---|---|---|
| 3-1 | 성공률 — 2xx+3xx 비율 | timeseries | `sum(rate(...{status=~"2..|3.."}[1m])) / sum(rate(...[1m])) * 100` | Mean, **Min** |
| 3-2 | 실패 — 5xx 비율 | timeseries | `sum(rate(...{status=~"5.."}[1m])) / sum(rate(...[1m])) * 100` | Max |
| 3-3 | 분당 5xx 건수 | timeseries | `sum(increase(http_server_requests_seconds_count{uri=~"/api/v1/.*",status=~"5.."}[1m]))` | Max |
| 3-4 | **[신규]** 폭풍 구간 누적 5xx | stat | `sum(increase(http_server_requests_seconds_count{uri=~"/api/v1/.*",status=~"5.."}[$__range]))` | 총 건수 (본문의 "14,708건"이 여기서 나온다) |
| 3-5 | **[신규]** 커넥션 획득 타임아웃 건수 | timeseries | `increase(hikaricp_connections_timeout_total{application="shelfeed"}[1m])` | 3-3과 **같은 모양·같은 높이**인지 |

- 3-5가 논증상 결정적이다. "5xx의 원인이 풀 타임아웃"을 지금 초안은 **말로만** 주장한다. 이 패널을 3-3 바로 옆에 두면 두 곡선이 포개져서 그림 한 장이 그 인과를 증명한다.
- y축은 0~100 고정. 자동 스케일이면 성공률 하락이 실제보다 극적으로 보인다.

## 파트 4 — 알림은 하나만 울렸다

**그림이 증명할 문장**: 나머지가 조용했던 게 아니라, 커넥션 풀·행 락 룰은 그때 아예 없었다.
**대시보드 패널 아님** — Grafana `Alerting → Alert rules` 화면 캡처 · 캔버스 대응: `AlertBefore`

들어갈 요소:
- 상단 `● 1 Firing` 배지
- 룰 `⓪ 감상글 상세 p99 1초 초과` 한 줄과 그 조건식
- **그 아래가 비어 있다는 사실 자체**가 이 그림의 내용이다

> 지금 저장소 상태가 마침 이 화면이다 — `view-lock-rules.yaml`이 ⓪ 하나만 남긴 임시 축소본이라 **사건 당시 화면을 그대로 캡처할 수 있다.** 파트 14 캡처 전에 7개 전체로 복원해야 한다.

## 파트 5 — DB는 한가했다

**그림이 증명할 문장**: DB가 더 많은 일을 하느라 느려진 게 아니다. 처리량은 오히려 늘었고 CPU도 여유가 있었다.
**행 이름**: `④ MySQL — 리소스 (무죄 증거)` · 캔버스 대응: `MysqlIdle`, `MysqlOverview`

| # | 요소 | 타입 | 쿼리 | 그림에서 읽을 수치 | 임계선 |
|---|---|---|---|---|---|
| 5-1 | Threads running / connected | timeseries (2선) | `mysql_global_status_threads_running` / `_threads_connected` | running Max | **20** (알람 ⑤) |
| 5-2 | 슬로우 쿼리 발생률 | timeseries | `rate(mysql_global_status_slow_queries[1m])` | Max | **0** (알람 ⑥) |
| 5-3 | MySQL QPS | timeseries | `rate(mysql_global_status_queries[1m])` | Max, Mean | — |
| 5-4 | 호스트 CPU | timeseries | `100 - avg(rate(node_cpu_seconds_total{mode="idle"}[1m])) * 100` | Max | — |

- 5-1 패널 description에 한 줄 **필수**: "락을 기다리는 세션도 running으로 센다." 안 적으면 "Threads running이 10으로 올랐는데 왜 무죄냐"에서 독자가 막힌다.
- 5-4 패널 description에 한 줄 **필수**: "cAdvisor가 없어 MySQL 컨테이너 CPU는 못 잰다. 이건 node-exporter가 본 호스트 CPU다." 초안의 "DB CPU·메모리 확인" 문장은 이 스택에서 성립하지 않는다.
- 5-1·5-2에 임계선을 그려두면 파트 14의 "⑤⑥은 Normal로 남는 대조군"이 같은 그림에서 미리 읽힌다.

## 파트 6 — 슬로우 쿼리 로그에는 다섯 줄이 남았다

**그림이 증명할 문장**: 쿼리가 느린 게 아니라 기다린 것이다. 슬로우 쿼리 로그는 개별 쿼리를 보지 경합을 보지 않는다.
**대시보드 요소 없음.** 터미널 캡처 (`mysql-perf` slow.log, `long_query_time=1`).
읽을 것: `Query_time: 1.0 / Lock_time: 1.0 / Rows_examined: 1`.

## 파트 7 — 커넥션 풀이 비어 있었다

**그림이 증명할 문장**: 풀이 작아서가 아니라 나간 커넥션이 돌아오지 않아서 비었다.
**행 이름**: `⑤ 커넥션 풀 (HikariCP)` · 캔버스 대응: `Hikari`, `AcquireUsage`, `HikariDashboard`

| # | 요소 | 타입 | 쿼리 | 그림에서 읽을 수치 | 임계선 |
|---|---|---|---|---|---|
| 7-1 | Active / Idle / Pending | timeseries (3선) | `hikaricp_connections_active` / `_idle` / `_pending` `{application="shelfeed"}` | Idle이 0으로 꺼지는 시각 = Pending이 솟는 시각 | **Max 8** (`hikaricp_connections_max`) |
| 7-2 | acquire / usage / creation **평균** 시간 | timeseries (3선) | `rate(hikaricp_connections_acquire_seconds_sum[1m]) / clamp_min(rate(..._count[1m]), 1e-9)` (usage·creation 동일) | acquire가 수 초로 오르는데 usage는 수십 ms에 머무는지, **creation이 0인지** | **1s**(알람 ②) · **5s**(커넥션 타임아웃) |
| 7-3 | **[신규]** Tomcat busy threads | timeseries | `tomcat_threads_busy_threads` | Pending과 같은 높이로 오르는지 | `threads.max` |

- 7-2의 creation 라인이 이 절의 숨은 주인공이다. "커넥션을 새로 만드느라 느린 것도 아니다"를 닫는 유일한 증거인데, 지금 초안은 이걸 빠뜨렸다.
- 7-2에 **5초 타임아웃 점선을 반드시 긋는다.** acquire가 그 선에 닿아 평평해지는 모양이 파트 3의 5xx와 이어지는 다리다.
- 7-3 신규 **(조건부)**: Pending 1,295가 나올 수 있었던 건 Tomcat 스레드를 2000으로 열어줬기 때문이다(기본 200이면 ~140에서 막힌다). 다만 **현재 본문에는 Tomcat을 언급하는 문장이 한 줄도 없다.** 원칙 1(절=행=그림)을 지키려면 둘 중 하나다 — 본문 7절에 "이 숫자가 나온 건 스레드를 열어줬기 때문"이라는 한 줄을 넣고 패널을 살리거나, 그 한 줄을 안 쓸 거면 패널을 빼는 것. **본문에 한 줄 넣는 쪽을 권한다.** 재현 조건을 감추면 Pending 1,295가 운영에서도 나오는 숫자처럼 읽힌다.

## 파트 8 — 커넥션을 붙잡고 있던 건 한 행의 락이었다

**그림이 증명할 문장**: 한 건이 오래 기다린 게 아니라 모든 커넥션이 거기 묶여 있었다.
**행 이름**: `⑥ MySQL — InnoDB 행 락 (원인)` · 캔버스 대응: `RowLockWaits`, `RowLockTime`, `LockWaitsSql`

| # | 요소 | 타입 | 쿼리 | 그림에서 읽을 수치 | 임계선 |
|---|---|---|---|---|---|
| 8-1 | 행 락 대기 발생률 | timeseries | `rate(mysql_global_status_innodb_row_lock_waits[1m])` | Max, Mean | **10/s** (알람 ③) |
| 8-2 | **[분리·독립]** 현재 행 락 대기 세션 수 | timeseries | `mysql_global_status_innodb_row_lock_current_waits` | Max가 **풀 크기와 같은지** | **8 = 풀 크기** |
| 8-3 | 행 락 평균 대기 시간 | timeseries | `rate(..._row_lock_time[1m]) / rate(..._row_lock_waits[1m])` | Max, Mean | **100ms** (알람 ④) |
| 8-4 | **[신규]** 락 대기가 풀 시간에서 차지한 비율 | stat (%) | `(rate(mysql_global_status_innodb_row_lock_time[1m]) / 1000) / max(hikaricp_connections_max{application="shelfeed"}) * 100` | 풀 전체 시간의 몇 %가 락 대기였나 |
| 8-5 | **[신규]** 감상글 상세 요청 중 락 앞에 선 비율 | stat (%) | `rate(mysql_global_status_innodb_row_lock_waits[1m]) / sum(rate(http_server_requests_seconds_count{uri="/api/v1/reviews/{reviewId}"}[1m])) * 100` | 상세 요청 몇 건 중 몇 건이 락 앞에 섰나 |
| 8-6 | `sys.innodb_lock_waits` | **터미널 캡처** | — | 막는 쪽·막히는 쪽이 같은 `review_id` |

- **8-2를 8-1에서 떼어내는 게 이 파트의 핵심 변경이다.** 기존 대시보드(패널 id5)는 발생률과 현재 대기 세션을 한 패널에 겹쳐 뒀는데, 단위가 다르고(`/s` vs 개) 축이 하나라 "대기 세션 최대치 = 풀 크기 8"이라는 **이 글에서 가장 중요한 일치**가 묻힌다. 풀 크기 8 점선을 깐 독립 패널로 세우면 그림 한 장이 끝낸다.
- 8-4·8-5 신규: 락 평균 대기가 33~94ms로 짧은데 왜 장애냐는 의문을 그림으로 막는다. **본문 8절 근거 표 세 줄이 이제 전부 패널을 갖는다** — 8-5가 "5건 중 4건이 락 앞에 섰다", 8-4가 "풀 시간의 74%", 8-2가 "동시 대기 세션 최대 8".
- **단위 주의.** `Innodb_row_lock_time`은 누적 **밀리초**이고 exporter가 변환 없이 노출한다. `rate(...[1m])`는 ms/s → `/1000`으로 s/s(= 평균 동시 락 대기 세션 수)가 되고, 풀 크기로 나누면 점유 비율이다. **`* 100`을 붙이거나 패널 unit을 `percentunit`으로 두 가지 중 하나만 택한다.** 둘 다 하면 100배로 찍힌다.
- 8-5의 분모는 "인기글"이 아니라 **감상글 상세 전체**다. Prometheus가 uri를 템플릿하기 때문이며, 본문에 인용할 때 그렇게 부른다.
- 8-3의 임계선 100ms는 실측에서 **울리지 않았다**(최대 94ms). 그 사실이 그림에 보이는 게 정직하고, 파트 14에서 "임계를 50ms로 낮출지" 논의의 근거가 된다.

2. **행 순서가 바뀌면 33개 패널의 gridPos를 다시 계산해야 하는데**, 생성기는 행에 패널을 순서대로 넣으면 좌표를 자동으로 잡는다. 블로그 절 순서가 바뀌어도 한 줄만 옮기면 된다.

## D-2. 왜 캔버스와 행 순서가 다른가

캔버스는 `①증상 ②막힌 곳 ③원인 ④무죄 증거`였다. 대시보드는 `개요 → 증상 → 사용자 영향 → DB 무죄 → 커넥션 풀 → 행 락`이다.

블로그는 **증상을 보고 → DB를 먼저 지우고 → 막힌 곳을 찾고 → 원인에 닿는** 순서로 좁혀 간다. 무죄 증거를 원인 뒤에 두면 "이미 범인을 아는데 왜 알리바이를 보나"가 되어 절이 죽는다. **행을 위에서 아래로 캡처하면 그대로 진단 순서가 되도록** 맞췄다.

## D-3. 패널 형태를 그렇게 정한 이유

| 결정 | 이유 |
|---|---|
| 성공률만 Min, 나머지는 Max | 떨어지는 지표에 Max를 쓰면 100%가 찍혀 아무 말도 못 한다 |
| 행 락 발생률과 현재 대기 세션을 **분리** | 단위가 `/s`와 개로 달라 한 축에 묶으면 "대기 세션 최대 = 풀 크기"라는 이 글의 핵심 일치가 묻힌다 |
| acquire 패널에 점선 **2개** | 알람 ② 임계(1s, 주황)와 커넥션 타임아웃(5s, 빨강) |
| acquire/usage를 `_max`가 아니라 **`rate(_sum)/rate(_count)` 평균**으로 | `_max`는 감쇠 창이라 워밍업 스파이크 잔여가 평시 구간까지 5초로 보인다(실측 8 그림에서 확인). 평균은 0 → 3.1초로 깨끗한 계단이 나오고, usage 12ms와 나란히 두면 "오래 잡아서"가 아니라 "짧게 잡는 걸 한 줄로 세워서"가 한 패널에서 읽힌다 |
| 커넥션 타임아웃 건수를 5xx 옆에 | "5xx의 원인이 풀 타임아웃"을 말이 아니라 두 곡선이 포개지는 그림으로 증명한다 |
| k6(InfluxDB) 라인을 따로 | Micrometer가 uri를 템플릿해 인기글과 다른 글이 한 시계열에 합쳐진다. 인기글 한 건만 떼어내는 유일한 방법이 k6의 `api` 태그다 |
| 행마다 해설 text 패널 | 행을 통째로 캡처했을 때 블로그 캡션에 쓸 문장이 그림 안에 같이 들어온다 |
| 누적 5xx만 instant 질의 | `$__range` 전체 합이라 구간마다 다시 계산할 이유가 없다 |

## D-4. 제작 중 잡은 결함

| 결함 | 증상 | 조치 |
|---|---|---|
| PromQL 벡터 매칭 실패 | 신규 stat 2개가 빈 결과. 좌변엔 exporter의 `instance`/`job` 라벨이 있고 집계 함수를 거친 우변엔 라벨이 없어 매칭 실패 | 분모를 `scalar()`로 감쌈 |
| Pending 임계 하드코딩 | 알람 ①은 `gt 0`인데 패널은 `1`로 박아 둠 — 단일 소스 원칙 위반 | `TH["shelfeed-pending"] + 1`로 유도(정수라 첫 나쁜 값이 0+1). 필수 검사 집합에 추가 |
| acquire 패널 점선 위치 | 설명문은 5초 타임아웃을 말하는데 점선은 1초에만 있었음 | 점선 2개로 변경 |
| Prometheus 데이터 볼륨 없음 | 보존 7d 설정인데도 컨테이너 재생성 때마다 TSDB 소멸. 지난 실측 3회분이 사라진 원인 | `prometheus-data` named volume 추가 |
| 알람 프로비저닝 미반영 | 룰 7개를 복원했는데 1개만 로드됨. 알람 프로비저닝은 **기동 시 1회만** 실행되고 대시보드처럼 폴링하지 않는다 | Grafana 재시작 필요 (아래 D-5) |

## D-5. 알람 화면 캡처는 부하를 두 번 돌려야 한다

알람 룰이 기동 시에만 적재되므로 두 화면을 한 번의 실행으로 얻을 수 없다.

| 캡처 | 필요한 상태 | 실행 |
|---|---|---|
| 파트 4 — "알림은 하나만 울렸다" | ⓪만 등록된 상태 | **1차 실행** (현재 상태가 정확히 이것) |
| 파트 14 — "3분 안에 알아채도록" | 7개 전부 등록 | Grafana 재시작 후 **2차 실행** |

③④는 `rate[5m]` + `for 5m`이라 폭풍이 5분보다 길어야 Firing까지 간다. 2차 실행도 폭풍 6분을 유지한다.
